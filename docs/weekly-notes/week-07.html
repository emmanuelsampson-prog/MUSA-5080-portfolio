2. Why Feature Engineering?

The machine learning method we are using is linear regression.

A linear model can only fit a straight line through the data.

More flexible machine learning methods can fit more complicated shapes. We are not using those yet.

Instead, we ask:

How much can we improve a linear regression by changing the shape of the features we give it?

Linear regression has real advantages:

  • It is interpretable
  • We can explain how it works
  • We understand what is happening “under the hood”

Therefore:

More complex methods are not automatically better. Linear regression is tried and tested, and it is a good model.

3. When a Straight Line Is Not Enough

Suppose we predict rent as a function of income.

Regression finds the best-fitting line between the dependent variable and the independent variables.

But what if the true relationship is not a straight line?

We can transform the features so that a straight line fits them better.

For each transformation, we will check whether it improves the cross-validated RMSE.

Technique Problem it addresses
Logs Skewed data, or percentage changes matter more than raw changes
Squared (polynomial) terms Curved relationships
Categorical variables Groups or thresholds
Interaction terms Slopes that differ by group
Fixed effects Unmeasured characteristics of a place

6. Creating a Point Feature for City Hall

Why?

One reason rents differ between neighbourhoods may be closeness to Center City.

To operationalize that idea, we create a point at City Hall and measure each tract’s distance to it.

This is the work of a feature engineer: turning an idea into a measurable variable.

How?

It is easiest to find coordinates as latitude and longitude. For example, click a location in Google Maps.

Those coordinates are in WGS84 (EPSG:4326), so:

  1. Create the point in EPSG:4326
  2. Transform it to State Plane feet (EPSG:2272) to match the tracts
#| eval: false
city_hall <- st_sfc(
  st_point(c(-75.1635, 39.9526)),  # longitude, latitude
  crs = 4326
) %>%
  st_transform(2272)

Always know which CRS your input coordinates are in before creating a point.

Note that st_point() takes longitude first, then latitude (x, y).

8. Why Drop Missing Values First?

In R:

!

means NOT. So !is.na(rent) keeps records where rent is not missing.

If a row has a missing value, lm() will quietly drop it, without telling you.

That creates a problem:

Different models could be estimated on different sets of tracts, so their RMSEs would not be directly comparable.

For fair comparisons, every model must use:

  • Exactly the same records
  • Exactly the same folds

After filtering, the dataset has:

377 census tracts

9. A Consistent Cross-Validation Helper Function

Goal

This week we want to see how changing the features changes the same model.

So we remove randomness in the fold assignment:

If a tract is in fold 1 the first time, it stays in fold 1 every time.

The caret package can also do train/test splits. Here, however, fixing the folds ourselves guarantees identical comparisons.

Setting the folds

#| eval: false
set.seed(5080)

folds <- sample(rep(1:10, length.out = nrow(tracts)))

set.seed() makes the random number generator reproducible. The course number, 5080, is used as the seed.

This randomly assigns each tract to one of 10 folds.

The function

#| eval: false
cv_rmse <- function(f, data, log_y = FALSE) {

  preds <- rep(NA, nrow(data))

  for (k in 1:10) {
    # Train on every fold except k
    m <- lm(f, data = data[folds != k, ])

    # Predict for the held-out fold k
    preds[folds == k] <- predict(m, newdata = data[folds == k, ])
  }

  # If the outcome was logged, convert predictions back to dollars
  if (log_y) preds <- exp(preds)

  sqrt(mean((data$rent - preds)^2))
}

How it works

For each fold k:

Fold k steps aside (test set)
        ↓
Fit lm() on all other folds (training set) → model m
        ↓
predict() rents for fold k using m's coefficients
        ↓
Compare predictions with actual rents

Every tract gets a turn in the test set.

A function is just a set of instructions that runs whenever it is called. Here we give it:

  • f: the regression formula
  • data: the dataset
  • log_y: whether the outcome was logged (explained in Section 14)

10. Root Mean Square Error (RMSE)

\[ RMSE = \sqrt{\frac{1}{n}\sum_{i=1}^{n}(y_i - \hat{y}_i)^2} \]

where:

  • \(y_i\) = actual rent
  • \(\hat{y}_i\) = predicted rent

RMSE is in the same units as the outcome: dollars of rent.

Lower RMSE = better out-of-sample prediction.

11. The Baseline Model and the Model Log

A model log is simply a record of each model and its result.

“Log” here means a record, not a logarithm.

It is stored as a tibble, and we add a row for every new model.

#| eval: false
f0 <- rent ~ income + pct_renters + building_age + dist_ch_mi

m0 <- lm(f0, data = tracts)

model_log <- tibble(
  model = "M0: Baseline",
  rmse  = cv_rmse(f0, tracts)
)

The baseline predicts rent as a function of:

  • Median household income
  • Percent renters
  • Building age
  • Distance to City Hall

Result

Baseline RMSE ≈ $265

On average, the baseline prediction for a tract’s median rent is off by about $265.

12. Trick 1: Log Transformations

When to use a log

1. Skewed distributions

If a variable has a long tail rather than a roughly normal distribution, taking the log can help. Linear regression works best with roughly normal data.

2. Theoretical reasons: percentage change matters

Consider income:

Change Raw increase Percentage change Meaning
$30,000 → $60,000 +$30,000 +100% Income doubles. A neighbourhood may move out of poverty
$170,000 → $200,000 +$30,000 ≈ +18% A modest bonus

The raw increase is identical, but the consequences are very different.

When percentage changes matter more than unit changes, consider a log.

Workflow

Look at the distribution
        ↓
Does it look skewed?
        ↓
Try a log and compare cross-validated RMSE

13. Logging a Predictor

The outcome (rent) stays the same. Simply write log() in the formula:

#| eval: false
f1 <- rent ~ log(income) + pct_renters + building_age + dist_ch_mi

m1 <- lm(f1, data = tracts)
coef(m1)

No separate transformation step is needed.

Interpreting the coefficient

\[ \hat{\beta}_{\log(income)} = 502 \]

For a 1% increase in income:

\[ \frac{\beta}{100} = \frac{502}{100} \approx \$5 \]

A 1% increase in median income is associated with about $5 more rent, holding the other variables constant.

For a 10% increase in income:

\[ \beta \times \log(1.10) = 502 \times 0.0953 \approx \$48 \]

A 10% increase in income is associated with roughly $50 more rent.

Interpreting coefficients is not our main goal in prediction. But it is worth checking that they pass a sniff test.

Adding it to the model log

#| eval: false
model_log <- model_log %>%
  add_row(model = "M1: log(income)", rmse = cv_rmse(f1, tracts))

Result

The RMSE did not really improve.

A log transformation does not guarantee a better fit.

14. Warning: Logs and Zeros

\[ \log(0) = -\infty \]

If a variable contains real zeros, lm() will fail.

Example: counts of crimes or 311 calls per tract. A zero means “no crimes”. It is real information, not missing data.

Do not drop zero observations just to take a log.

Instead, use:

#| eval: false
log1p(x)

which computes:

\[ \log(1 + x) \]

so that:

\[ \log(1 + 0) = 0 \]

The transcript records this as “log1px”. The correct R function is log1p().

15. Logging the Outcome Variable

If rent is skewed, we can log the outcome instead of, or as well as, the predictors.

#| eval: false
f2 <- log(rent) ~ log(income) + pct_renters + building_age + dist_ch_mi

This is a log–log model for income.

You can go “log crazy”, but this is not recommended.

16. Interpreting Log Models

Model Form Interpretation of β
Level–level \(y \sim x\) 1-unit ↑ in x → β units change in y (the slope)
Level–log \(y \sim \log(x)\) 1% ↑ in x → β / 100 units change in y
Log–level \(\log(y) \sim x\) 1-unit ↑ in x → approx. 100 × β % change in y
Log–log \(\log(y) \sim \log(x)\) 1% ↑ in x → approx. β % change in y

The log–log coefficient is an elasticity, a familiar idea from economics.

In the lecture, the level–level case was described as “a β percent increase in y”. The correct reading is β units of y.

You do not need to memorize these. Prediction is our main focus. But you should know where to look them up.

17. Critical Warning: Log Dollars

When the outcome is logged, the RMSE suddenly looks amazing:

Before: RMSE ≈ 265
After:  RMSE ≈ 0.18

This is not a breakthrough.

The second number is in log dollars.

Your boss does not speak log dollars. They want to know how many dollars the model is off by.

So we must convert predictions back to dollars by taking the exponent:

\[ \hat{y} = e^{\widehat{\log(y)}} \]

This is what the log_y = TRUE argument in cv_rmse() does:

#| eval: false
model_log <- model_log %>%
  add_row(
    model = "M2: log(rent) + log(income)",
    rmse  = cv_rmse(f2, tracts, log_y = TRUE)
  )

Result

The RMSE improved by about $2.

18. Trick 2: Squared (Polynomial) Terms

Non-linear relationships

If a scatter plot shows a curve, we can still use a linear model. We just “trick” it by adding a squared term.

Classic example: building age

New buildings      → higher rent (new and shiny; built in desirable areas)
Middle-aged        → lower rent (dated, not updated)
Very old buildings → higher rent again ("vintage")

So the relationship between age and rent is often U-shaped:

Rent
 │ ●                       ●
 │   ●                   ●
 │     ●             ●
 │        ●  ●  ●
 └──────────────────────────── Building age
   new     middle-aged     old

A data artifact to watch for

The Census records every building built before 1940 as “1939 or earlier”.

All of those tracts get the same value, which creates a pile-up at the oldest ages.

Discover artifacts like this through exploratory data analysis. Always plot your data (scatter plots!) after collecting it.

19. Adding a Squared Term with I()

#| eval: false
f3 <- rent ~ log(income) + pct_renters + building_age +
  I(building_age^2) + dist_ch_mi

m3 <- lm(f3, data = tracts)

I() means “do the math”: compute building_age^2 as a new variable.

Without I(), R quietly ignores the squared term or gives a syntax error.

Keep both the linear term and the squared term in the model.

20. Reading the Two Coefficients Together

The model now estimates:

\[ y = \beta_0 + \beta_1 x + \beta_2 x^2 + \dots \]

The signs of \(\beta_1\) and \(\beta_2\) together describe the shape:

Linear term \(\beta_1\) Squared term \(\beta_2\) Shape
+ − Rises, then levels off or falls (∩)
− + Falls, then rises (∪)

In our model:

  • \(\beta_1\) (building age) is negative → rent falls as buildings age
  • \(\beta_2\) (building age²) is positive → eventually rent rises again

This picks up the non-linear “vintage” pattern we expected.

21. The Turning Point

Where does the effect switch from negative to positive?

\[ x^* = -\frac{\beta_1}{2\beta_2} \]

where:

  • \(\beta_1\) = coefficient on the linear term
  • \(\beta_2\) = coefficient on the squared term
#| eval: false
b1 <- coef(m3)["building_age"]
b2 <- coef(m3)["I(building_age^2)"]

turning_point <- -b1 / (2 * b2)
turning_point

Result

\[ x^* \approx 76.8 \text{ years} \]

Around 77 years old, buildings become “vintage enough” that age starts to add to rent.

Check: is the turning point inside your data?

#| eval: false
max(tracts$building_age)

In our data, the maximum building age is about 85 years, so the turning point is within the observed range.

If the turning point were far outside your data (for example, 200 years), the parabola would only bend. It would not actually turn within the data.

Don’t tell a story about a turn you never observed.

Result

#| eval: false
model_log <- model_log %>%
  add_row(model = "M3: + building age²", rmse = cv_rmse(f3, tracts))

RMSE fell by about another $2, to roughly $261.

22. Trick 3: Categorical Variables

Two reasons to use categories

1. The data already come in categories

  • Zoning class
  • Housing type
  • Inside a TOD area or not
  • Planning district

Categories may be binary (yes/no) or have several groups.

2. We create our own categories

When a continuous variable seems to behave like groups rather than a straight line.

Example: distance rings

Instead of assuming rent declines steadily with distance from City Hall, we might assume:

Ring Distance from City Hall
Core Under 2 miles
Inner 2 to under 5 miles
Outer 5 miles or more

The idea: being 0.2 miles or 2 miles from City Hall has roughly the same effect. Both are “core”.

23. Creating Categories with case_when()

#| eval: false
tracts <- tracts %>%
  mutate(
    ring = case_when(
      dist_ch_mi < 2 ~ "Core",
      dist_ch_mi < 5 ~ "Inner",
      TRUE           ~ "Outer"
    ),
    ring = factor(ring)
  )
  • Conditions are checked in order
  • TRUE catches everyone else who did not meet the earlier conditions

Why factor()?

A factor tells R that the values are groups, not numbers.

This matters most when categories are labelled with numbers:

1, 2, 3

Without factor(), R treats them as ordinal or continuous numbers, as if 1 < 2 < 3.

Use factor() so categories are treated as labels, not quantities.

24. Always Count Your Categories

#| eval: false
tracts %>%
  st_drop_geometry() %>%
  count(ring)

This is where 99% of your cross-validation problems will come from.

Why?

Suppose only 3 tracts are in the core, and all three land in the same test fold:

Training data: no core tracts
        ↓
Model never estimates a coefficient for "Core"
        ↓
Test data: "We're core!"
        ↓
Model: "I've never heard of core" → error

Make sure every category has enough observations for both the regression and cross-validation.

26. Dummy Coding and the Reference Category

Behind the scenes, R converts each category into binary (0/1) variables:

Tract ring Inner Outer
A Core 0 0
B Inner 1 0
C Outer 0 1

A tract that is neither Inner nor Outer must be Core.

Why k − 1?

Because of the math, a model cannot include all category dummies and an intercept.

With \(k\) categories, R estimates:

\[ k - 1 \]

dummy variables.

Here:

\[ k = 3 \quad (\text{Core, Inner, Outer}) \Rightarrow k - 1 = 2 \]

The left-out category is the reference category. Its effect is absorbed into the intercept.

Category coefficients are always interpreted relative to the reference category.

27. Interpreting Category Coefficients

#| eval: false
f4 <- rent ~ log(income) + pct_renters + building_age +
  I(building_age^2) + ring

m4 <- lm(f4, data = tracts)
coef(m4)
Ring Coefficient Interpretation
Core Reference (absorbed in intercept)
Inner −122 Inner-ring tracts rent for $122 less than core tracts, all else equal
Outer −164 Outer-ring tracts rent for $164 less than core tracts, all else equal

Changing the reference category

By default, R chooses the reference alphabetically (“Core” comes first).

#| eval: false
tracts <- tracts %>%
  mutate(ring = relevel(ring, ref = "Outer"))

Now the interpretation becomes:

Compared with the outer ring, core tracts rent for about $160 more.

Changing the reference category changes the interpretation, not the predictions.

28. Trade-off: Categories Throw Away Information

Replacing continuous distance with three rings means:

2.1 miles → Inner
4.9 miles → Inner

Both are treated identically, even though they are almost 3 miles apart.

You can include both the continuous variable and the categories, but check that this does not destabilize the model.

Result

#| eval: false
model_log <- model_log %>%
  add_row(model = "M4: rings instead of distance", rmse = cv_rmse(f4, tracts))

The RMSE got worse.

It was not a great example, but it does not hurt to try. Consider categories when:

  • The data look jumpy or grouped
  • You have a strong theoretical reason

29. Trick 4: Interaction Terms

Categories vs. interactions

Technique What changes by group?
Categorical variable The intercept (the level shifts up or down)
Interaction term The slope (the relationship itself differs)

Hypothesis

The relationship between income and rent may differ by ring:

  • Steeper in Center City
  • Flatter further out, where income matters less

Code

Multiply the terms inside the formula:

#| eval: false
f5 <- rent ~ log(income) * ring + pct_renters +
  building_age + I(building_age^2)

m5 <- lm(f5, data = tracts)
coef(m5)

log(income) * ring includes:

  • log(income) main effect
  • ring main effects
  • log(income):ring interaction terms

30. Interpreting Interaction Coefficients

Term Coefficient Meaning
log(income) 653 Slope in the Core (reference)
log(income):ringInner −219 Inner-ring slope is 219 less → ≈ 434
log(income):ringOuter −244 Outer-ring slope is 244 less → ≈ 409

So the income–rent relationship is indeed strongest in the core.

Result

#| eval: false
model_log <- model_log %>%
  add_row(model = "M5: log(income) × ring", rmse = cv_rmse(f5, tracts))

RMSE ≈ $264: better than M4, but worse than the best model so far.

Use interactions when you have a reason, not “willy-nilly”. Models quickly become untenable.

31. Trick 5: Fixed Effects

The idea

Suppose you have included everything you can measure:

  • Distance to the core
  • Income
  • Share of people with a bachelor’s degree
  • Bike share stations
  • …

There may still be unmeasurable factors that explain why rent is higher in some places:

  • Sense of place
  • Perception
  • Reputation

A fixed effect is a catch-all:

A dummy variable for an area that absorbs the remaining variation explained simply by being located there.

Choosing the area

Our outcome is already measured at the tract level, so the fixed effect must be a larger area.

We use Philadelphia’s:

18 planning districts

32. Assigning Tracts to Planning Districts

#| eval: false
districts <- st_read("planning_districts.geojson") %>%
  st_transform(2272)

tracts <- tracts %>%
  st_join(
    districts %>% select(district = DIST_NAME),
    largest = TRUE
  ) %>%
  mutate(district = factor(district))

The file name and the DIST_NAME field are illustrative. Use the names in the course code.

Spatial join with largest = TRUE

What if a tract is split by two districts?

┌───────────────┐
│ District 1    │ District 2
│   ███████████ │ ████
│   ███ tract ██│ ████
└───────────────┘

largest = TRUE assigns the whole tract to the district containing the largest share of its area.

Unlike st_intersection(), the tract is not cut. It receives one district value.

Why factor() again?

District numbers are labels, not rankings. District 1 is not “less than” District 2.

33. Small Categories Break Cross-Validation

#| eval: false
tracts %>%
  st_drop_geometry() %>%
  count(district, sort = TRUE)

In the lecture, one district (Lower South) contained very few tracts.

This caused two problems:

  1. When those tracts were in the test fold, the training model had never learned their coefficient → error
  2. Estimating a coefficient from one observation is highly unstable

Fix

Make sure every category has at least about 10 observations.

Options:

  • Combine small categories into an “Other” group (works, but not ideal)
  • Merge a small district with a neighbouring district (better)
#| eval: false
small <- tracts %>%
  st_drop_geometry() %>%
  count(district) %>%
  filter(n < 10) %>%
  pull(district)

tracts <- tracts %>%
  mutate(
    district = as.character(district),
    district = if_else(district %in% small, "Other", district),
    district = factor(district)
  )

34. Estimating the Fixed Effects Model

#| eval: false
f6 <- log(rent) ~ log(income) + pct_renters + building_age +
  I(building_age^2) + dist_ch_mi + district

m6 <- lm(f6, data = tracts)

Here the fixed effects are added to the best model so far. Check the course code for the exact formula.

What do we get?

Each district gets its own intercept.

Mapping these intercepts shows the “value” of being in each district, which is useful information in itself.

Did the fixed effects absorb spatial clustering?

Comparing maps of residuals before and after adding district fixed effects shows only minor differences.

Result

#| eval: false
model_log <- model_log %>%
  add_row(model = "M6: + district fixed effects",
          rmse  = cv_rmse(f6, tracts, log_y = TRUE))

RMSE ≈ $256: the best model.

  • Create points from latitude/longitude in EPSG:4326, then transform to the project CRS.

  • log(0) is −∞. Use log1p() for variables with real zeros.
  • With a logged outcome, back-transform predictions with exp() before computing RMSE. Otherwise the error is in log dollars.
  • Log–log coefficients are elasticities.
  • Squared terms, written with I(x^2), capture curved relationships.

## 2. Why Feature Engineering?

The machine learning method we are using is **linear regression**.

A linear model can only fit a **straight line** through the data.

More flexible machine learning methods can fit more complicated shapes. We are not using those yet.

Instead, we ask:

> **How much can we improve a linear regression by changing the shape of the features we give it?**

Linear regression has real advantages:

- It is **interpretable**
- We can **explain** how it works
- We understand what is happening "under the hood"

Therefore:

> **More complex methods are not automatically better. Linear regression is tried and tested, and it is a good model.**

## 3. When a Straight Line Is Not Enough

Suppose we predict rent as a function of income.

Regression finds the best-fitting line between the dependent variable and the independent variables.

But what if the true relationship is **not** a straight line?

We can transform the features so that a straight line fits them better.

For each transformation, we will check whether it **improves the cross-validated RMSE**.

| Technique | Problem it addresses |
|---|---|
| Logs | Skewed data, or percentage changes matter more than raw changes |
| Squared (polynomial) terms | Curved relationships |
| Categorical variables | Groups or thresholds |
| Interaction terms | Slopes that differ by group |
| Fixed effects | Unmeasured characteristics of a place |

In R:

means **NOT**. So `!is.na(rent)` keeps records where rent is **not** missing.

## 9. A Consistent Cross-Validation Helper Function

### Goal

This week we want to see how **changing the features** changes the **same model**.

So we remove randomness in the fold assignment:

> **If a tract is in fold 1 the first time, it stays in fold 1 every time.**

The `caret` package can also do train/test splits. Here, however, fixing the folds ourselves guarantees identical comparisons.

### Setting the folds

```r
#| eval: false
set.seed(5080)

folds <- sample(rep(1:10, length.out = nrow(tracts)))
```

`set.seed()` makes the random number generator reproducible. The course number, 5080, is used as the seed.

This randomly assigns each tract to one of **10 folds**.

### The function

```r
#| eval: false
cv_rmse <- function(f, data, log_y = FALSE) {

  preds <- rep(NA, nrow(data))

  for (k in 1:10) {
    # Train on every fold except k
    m <- lm(f, data = data[folds != k, ])

    # Predict for the held-out fold k
    preds[folds == k] <- predict(m, newdata = data[folds == k, ])
  }

  # If the outcome was logged, convert predictions back to dollars
  if (log_y) preds <- exp(preds)

  sqrt(mean((data$rent - preds)^2))
}
```

### How it works

For each fold `k`:

```text
Fold k steps aside (test set)
        ↓
Fit lm() on all other folds (training set) → model m
        ↓
predict() rents for fold k using m's coefficients
        ↓
Compare predictions with actual rents
```

Every tract gets a turn in the test set.

A function is just a **set of instructions** that runs whenever it is called. Here we give it:

- `f`: the regression formula
- `data`: the dataset
- `log_y`: whether the outcome was logged (explained in Section 14)

## 10. Root Mean Square Error (RMSE)

$$
RMSE = \sqrt{\frac{1}{n}\sum_{i=1}^{n}(y_i - \hat{y}_i)^2}
$$

where:

- $y_i$ = actual rent
- $\hat{y}_i$ = predicted rent

RMSE is in the **same units as the outcome**: dollars of rent.

> **Lower RMSE = better out-of-sample prediction.**

## 12. Trick 1: Log Transformations

### When to use a log

**1. Skewed distributions**

If a variable has a **long tail** rather than a roughly normal distribution, taking the log can help. Linear regression works best with roughly normal data.

**2. Theoretical reasons: percentage change matters**

Consider income:

| Change | Raw increase | Percentage change | Meaning |
|---|---:|---:|---|
| $30,000 → $60,000 | +$30,000 | +100% | Income doubles. A neighbourhood may move out of poverty |
| $170,000 → $200,000 | +$30,000 | ≈ +18% | A modest bonus |

The **raw** increase is identical, but the consequences are very different.

> **When percentage changes matter more than unit changes, consider a log.**

### Workflow

```text
Look at the distribution
        ↓
Does it look skewed?
        ↓
Try a log and compare cross-validated RMSE
```

---

## 13. Logging a Predictor

The outcome (rent) stays the same. Simply write `log()` in the formula:

```r
#| eval: false
f1 <- rent ~ log(income) + pct_renters + building_age + dist_ch_mi

m1 <- lm(f1, data = tracts)
coef(m1)
```

No separate transformation step is needed.

### Interpreting the coefficient

$$
\hat{\beta}_{\log(income)} = 502
$$

**For a 1% increase in income:**

$$
\frac{\beta}{100} = \frac{502}{100} \approx \$5
$$

> **A 1% increase in median income is associated with about $5 more rent, holding the other variables constant.**

**For a 10% increase in income:**

$$
\beta \times \log(1.10) = 502 \times 0.0953 \approx \$48
$$

> **A 10% increase in income is associated with roughly $50 more rent.**

Interpreting coefficients is not our main goal in prediction. But it is worth checking that they pass a **sniff test**.

### Adding it to the model log

```r
#| eval: false
model_log <- model_log %>%
  add_row(model = "M1: log(income)", rmse = cv_rmse(f1, tracts))
```

### Result

> **The RMSE did not really improve.**

A log transformation does not guarantee a better fit.

## 14. Warning: Logs and Zeros

$$
\log(0) = -\infty
$$

If a variable contains **real zeros**, `lm()` will fail.

Example: counts of crimes or 311 calls per tract. A zero means "no crimes". It is real information, not missing data.

> **Do not drop zero observations just to take a log.**

Instead, use:

```r
#| eval: false
log1p(x)
```

which computes:

$$
\log(1 + x)
$$

so that:

$$
\log(1 + 0) = 0
$$

The transcript records this as "log1px". The correct R function is `log1p()`.

---

## 15. Logging the Outcome Variable

If **rent** is skewed, we can log the **outcome** instead of, or as well as, the predictors.

```r
#| eval: false
f2 <- log(rent) ~ log(income) + pct_renters + building_age + dist_ch_mi
```

This is a **log–log** model for income.

You can go "log crazy", but this is **not** recommended.

---

## 16. Interpreting Log Models

| Model | Form | Interpretation of β |
|---|---|---|
| Level–level | $y \sim x$ | 1-unit ↑ in x → **β units** change in y (the slope) |
| Level–log | $y \sim \log(x)$ | 1% ↑ in x → **β / 100 units** change in y |
| Log–level | $\log(y) \sim x$ | 1-unit ↑ in x → approx. **100 × β %** change in y |
| Log–log | $\log(y) \sim \log(x)$ | 1% ↑ in x → approx. **β %** change in y |

The log–log coefficient is an **elasticity**, a familiar idea from economics.

In the lecture, the level–level case was described as "a β percent increase in y". The correct reading is **β units of y**.

> **You do not need to memorize these. Prediction is our main focus. But you should know where to look them up.**

---

## 17. Critical Warning: Log Dollars

When the outcome is logged, the RMSE suddenly looks amazing:

```text
Before: RMSE ≈ 265
After:  RMSE ≈ 0.18
```

This is **not** a breakthrough.

The second number is in **log dollars**.

> **Your boss does not speak log dollars. They want to know how many dollars the model is off by.**

So we must convert predictions back to dollars by taking the exponent:

$$
\hat{y} = e^{\widehat{\log(y)}}
$$

This is what the `log_y = TRUE` argument in `cv_rmse()` does:

```r
#| eval: false
model_log <- model_log %>%
  add_row(
    model = "M2: log(rent) + log(income)",
    rmse  = cv_rmse(f2, tracts, log_y = TRUE)
  )
```

### Result

> **The RMSE improved by about $2.**

## 18. Trick 2: Squared (Polynomial) Terms

### Non-linear relationships

If a scatter plot shows a **curve**, we can still use a linear model. We just "trick" it by adding a squared term.

### Classic example: building age

```text
New buildings      → higher rent (new and shiny; built in desirable areas)
Middle-aged        → lower rent (dated, not updated)
Very old buildings → higher rent again ("vintage")
```

So the relationship between age and rent is often **U-shaped**:

```text
Rent
 │ ●                       ●
 │   ●                   ●
 │     ●             ●
 │        ●  ●  ●
 └──────────────────────────── Building age
   new     middle-aged     old
```

### A data artifact to watch for

The Census records every building built before 1940 as **"1939 or earlier"**.

All of those tracts get the same value, which creates a pile-up at the oldest ages.

> **Discover artifacts like this through exploratory data analysis. Always plot your data (scatter plots!) after collecting it.**

---

## 19. Adding a Squared Term with `I()`

```r
#| eval: false
f3 <- rent ~ log(income) + pct_renters + building_age +
  I(building_age^2) + dist_ch_mi

m3 <- lm(f3, data = tracts)
```

`I()` means **"do the math"**: compute `building_age^2` as a new variable.

> **Without `I()`, R quietly ignores the squared term or gives a syntax error.**

Keep **both** the linear term and the squared term in the model.

---

## 20. Reading the Two Coefficients Together

The model now estimates:

$$
y = \beta_0 + \beta_1 x + \beta_2 x^2 + \dots
$$

The signs of $\beta_1$ and $\beta_2$ together describe the shape:

| Linear term $\beta_1$ | Squared term $\beta_2$ | Shape |
|---|---|---|
| + | − | Rises, then levels off or falls (∩) |
| − | + | Falls, then rises (∪) |

In our model:

- $\beta_1$ (building age) is **negative** → rent falls as buildings age
- $\beta_2$ (building age²) is **positive** → eventually rent rises again

> **This picks up the non-linear "vintage" pattern we expected.**

---

## 21. The Turning Point

Where does the effect switch from negative to positive?

$$
x^* = -\frac{\beta_1}{2\beta_2}
$$

where:

- $\beta_1$ = coefficient on the linear term
- $\beta_2$ = coefficient on the squared term

```r
#| eval: false
b1 <- coef(m3)["building_age"]
b2 <- coef(m3)["I(building_age^2)"]

turning_point <- -b1 / (2 * b2)
turning_point
```

### Result

$$
x^* \approx 76.8 \text{ years}
$$

> **Around 77 years old, buildings become "vintage enough" that age starts to add to rent.**

### Check: is the turning point inside your data?

```r
#| eval: false
max(tracts$building_age)
```

In our data, the maximum building age is about **85 years**, so the turning point is **within** the observed range.

If the turning point were far outside your data (for example, 200 years), the parabola would only **bend**. It would not actually turn within the data.

> **Don't tell a story about a turn you never observed.**

### Result

```r
#| eval: false
model_log <- model_log %>%
  add_row(model = "M3: + building age²", rmse = cv_rmse(f3, tracts))
```

> **RMSE fell by about another $2, to roughly $261.**

## 22. Trick 3: Categorical Variables

### Two reasons to use categories

**1. The data already come in categories**

- Zoning class
- Housing type
- Inside a TOD area or not
- Planning district

Categories may be **binary** (yes/no) or have **several groups**.

**2. We create our own categories**

When a continuous variable seems to behave like **groups** rather than a straight line.

### Example: distance rings

Instead of assuming rent declines steadily with distance from City Hall, we might assume:

| Ring | Distance from City Hall |
|---|---|
| Core | Under 2 miles |
| Inner | 2 to under 5 miles |
| Outer | 5 miles or more |

The idea: being 0.2 miles or 2 miles from City Hall has roughly the **same effect**. Both are "core".

---

## 23. Creating Categories with `case_when()`

```r
#| eval: false
tracts <- tracts %>%
  mutate(
    ring = case_when(
      dist_ch_mi < 2 ~ "Core",
      dist_ch_mi < 5 ~ "Inner",
      TRUE           ~ "Outer"
    ),
    ring = factor(ring)
  )
```

- Conditions are checked **in order**
- `TRUE` catches **everyone else** who did not meet the earlier conditions

### Why `factor()`?

A factor tells R that the values are **groups**, not numbers.

This matters most when categories are labelled with numbers:

```text
1, 2, 3
```

Without `factor()`, R treats them as **ordinal or continuous numbers**, as if 1 < 2 < 3.

> **Use `factor()` so categories are treated as labels, not quantities.**

---

## 24. Always Count Your Categories

```r
#| eval: false
tracts %>%
  st_drop_geometry() %>%
  count(ring)
```

> **This is where 99% of your cross-validation problems will come from.**

### Why?

Suppose only **3 tracts** are in the core, and all three land in the **same test fold**:

```text
Training data: no core tracts
        ↓
Model never estimates a coefficient for "Core"
        ↓
Test data: "We're core!"
        ↓
Model: "I've never heard of core" → error
```

> **Make sure every category has enough observations for both the regression and cross-validation.**

---

## 25. Evenly Spaced Bins with `cut()`

Instead of choosing thresholds from theory, `cut()` divides a variable into **evenly spaced bins**.

```r
#| eval: false
tracts <- tracts %>%
  mutate(
    renter_group = cut(
      pct_renters,
      breaks = 3,
      labels = c("Mostly Owners", "Mixed", "Mostly Renters")
    )
  )
```

| Category | Number of tracts |
|---|---:|
| Mostly Owners | 88 |
| Mixed | 210 |
| Mostly Renters | 79 |
| **Total** | **377** |

## 26. Dummy Coding and the Reference Category

Behind the scenes, R converts each category into **binary (0/1) variables**:

| Tract | ring | Inner | Outer |
|---|---|---:|---:|
| A | Core | 0 | 0 |
| B | Inner | 1 | 0 |
| C | Outer | 0 | 1 |

A tract that is neither Inner nor Outer must be **Core**.

### Why k − 1?

Because of the math, a model cannot include **all** category dummies **and** an intercept.

With $k$ categories, R estimates:

$$
k - 1
$$

dummy variables.

Here:

$$
k = 3 \quad (\text{Core, Inner, Outer}) \Rightarrow k - 1 = 2
$$

The left-out category is the **reference category**. Its effect is **absorbed into the intercept**.

> **Category coefficients are always interpreted relative to the reference category.**

---

## 27. Interpreting Category Coefficients

```r
#| eval: false
f4 <- rent ~ log(income) + pct_renters + building_age +
  I(building_age^2) + ring

m4 <- lm(f4, data = tracts)
coef(m4)
```

| Ring | Coefficient | Interpretation |
|---|---:|---|
| Core | Reference | (absorbed in intercept) |
| Inner | −122 | Inner-ring tracts rent for **$122 less** than core tracts, all else equal |
| Outer | −164 | Outer-ring tracts rent for **$164 less** than core tracts, all else equal |

### Changing the reference category

By default, R chooses the reference **alphabetically** ("Core" comes first).

```r
#| eval: false
tracts <- tracts %>%
  mutate(ring = relevel(ring, ref = "Outer"))
```

Now the interpretation becomes:

> **Compared with the outer ring, core tracts rent for about $160 more.**

> **Changing the reference category changes the interpretation, not the predictions.**

---

## 28. Trade-off: Categories Throw Away Information

Replacing continuous distance with three rings means:

```text
2.1 miles → Inner
4.9 miles → Inner
```

Both are treated identically, even though they are almost 3 miles apart.

You can include both the continuous variable and the categories, but check that this does not destabilize the model.

### Result

```r
#| eval: false
model_log <- model_log %>%
  add_row(model = "M4: rings instead of distance", rmse = cv_rmse(f4, tracts))
```

> **The RMSE got worse.**

It was not a great example, but it does not hurt to try. Consider categories when:

- The data look **jumpy** or **grouped**
- You have a strong **theoretical reason**

---

## 29. Trick 4: Interaction Terms

### Categories vs. interactions

| Technique | What changes by group? |
|---|---|
| Categorical variable | The **intercept** (the level shifts up or down) |
| Interaction term | The **slope** (the relationship itself differs) |

### Hypothesis

The relationship between **income** and **rent** may differ by ring:

- **Steeper** in Center City
- **Flatter** further out, where income matters less

### Code

Multiply the terms inside the formula:

```r
#| eval: false
f5 <- rent ~ log(income) * ring + pct_renters +
  building_age + I(building_age^2)

m5 <- lm(f5, data = tracts)
coef(m5)
```

`log(income) * ring` includes:

- `log(income)` main effect
- `ring` main effects
- `log(income):ring` interaction terms

---

## 30. Interpreting Interaction Coefficients

| Term | Coefficient | Meaning |
|---|---:|---|
| `log(income)` | 653 | Slope in the **Core** (reference) |
| `log(income):ringInner` | −219 | Inner-ring slope is 219 less → ≈ 434 |
| `log(income):ringOuter` | −244 | Outer-ring slope is 244 less → ≈ 409 |

So the income–rent relationship is indeed **strongest in the core**.

### Result

```r
#| eval: false
model_log <- model_log %>%
  add_row(model = "M5: log(income) × ring", rmse = cv_rmse(f5, tracts))
```

> **RMSE ≈ $264: better than M4, but worse than the best model so far.**

> **Use interactions when you have a reason, not "willy-nilly". Models quickly become untenable.**

## 31. Trick 5: Fixed Effects

### The idea

Suppose you have included everything you can measure:

- Distance to the core
- Income
- Share of people with a bachelor's degree
- Bike share stations
- …

There may still be **unmeasurable** factors that explain why rent is higher in some places:

- Sense of place
- Perception
- Reputation

A **fixed effect** is a catch-all:

> **A dummy variable for an area that absorbs the remaining variation explained simply by being located there.**

### Choosing the area

Our outcome is already measured at the **tract** level, so the fixed effect must be a **larger** area.

We use Philadelphia's:

> **18 planning districts**

---

## 32. Assigning Tracts to Planning Districts

```r
#| eval: false
districts <- st_read("planning_districts.geojson") %>%
  st_transform(2272)

tracts <- tracts %>%
  st_join(
    districts %>% select(district = DIST_NAME),
    largest = TRUE
  ) %>%
  mutate(district = factor(district))
```

The file name and the `DIST_NAME` field are illustrative. Use the names in the course code.

### Spatial join with `largest = TRUE`

What if a tract is split by two districts?

```text
┌───────────────┐
│ District 1    │ District 2
│   ███████████ │ ████
│   ███ tract ██│ ████
└───────────────┘
```

`largest = TRUE` assigns the **whole tract** to the district containing the **largest share of its area**.

> **Unlike `st_intersection()`, the tract is not cut. It receives one district value.**

### Why `factor()` again?

District numbers are **labels**, not rankings. District 1 is not "less than" District 2.

---

## 33. Small Categories Break Cross-Validation

```r
#| eval: false
tracts %>%
  st_drop_geometry() %>%
  count(district, sort = TRUE)
```

In the lecture, one district (**Lower South**) contained very few tracts.

This caused two problems:

1. When those tracts were in the test fold, the training model had **never learned** their coefficient → **error**
2. Estimating a coefficient from one observation is **highly unstable**

### Fix

> **Make sure every category has at least about 10 observations.**

Options:

- Combine small categories into an **"Other"** group (works, but not ideal)
- **Merge** a small district with a **neighbouring** district (better)

```r
#| eval: false
small <- tracts %>%
  st_drop_geometry() %>%
  count(district) %>%
  filter(n < 10) %>%
  pull(district)

tracts <- tracts %>%
  mutate(
    district = as.character(district),
    district = if_else(district %in% small, "Other", district),
    district = factor(district)
  )
```

#| eval: false
f6 <- log(rent) ~ log(income) + pct_renters + building_age +
  I(building_age^2) + dist_ch_mi + district

m6 <- lm(f6, data = tracts)

Here the fixed effects are added to the best model so far. Check the course code for the exact formula.

### What do we get?

Each district gets its **own intercept**.

## 38. Key Concepts to Remember

- Linear regression fits a straight line, but **feature engineering** lets it capture more complex relationships.
- Linear regression is **interpretable**. More complex methods are not automatically better.
- Feature engineering means **operationalizing ideas** (such as "closeness to Center City") as measurable variables.
- Create points from latitude/longitude in `EPSG:4326`, then transform to the project CRS.
- `lm()` **quietly drops** rows with missing values, so filter NAs before comparing models.
- Compare models using the **same records** and the **same folds**.
- A **model log** is a record of models and RMSEs, not a logarithm.
- Log transformations help with **skewed data** and when **percentage changes** matter.
- `log(0)` is −∞. Use `log1p()` for variables with real zeros.
- With a **logged outcome**, back-transform predictions with `exp()` before computing RMSE. Otherwise the error is in **log dollars**.
- Log–log coefficients are **elasticities**.
- Squared terms, written with `I(x^2)`, capture **curved** relationships.
- Read the linear and squared coefficients **together** to understand the shape.
- The turning point is **−β₁ / (2β₂)**. Check that it falls **inside the data range**.
- Always do **exploratory analysis**. The Census groups all pre-1940 buildings as "1939 or earlier".
- Use `factor()` so categories are treated as groups, not numbers.
- Categorical variables are dummy coded into **k − 1** variables. The omitted group is the **reference category**.
- Category coefficients are interpreted **relative to the reference**. Changing the reference changes interpretation, not predictions.
- Turning a continuous variable into categories **throws away information**.
- Categorical variables shift the **intercept**. Interaction terms let the **slope** vary by group.
- Use interactions only **when you have a reason**.
- **Fixed effects** absorb unmeasured characteristics of place, such as reputation and sense of place.
- `st_join(..., largest = TRUE)` assigns each polygon to the area containing most of it.
- **Always count observations per category**. Small categories break cross-validation. Aim for **at least ~10**.
- Fixed effects gave the **best model (≈ $256 RMSE)**.
